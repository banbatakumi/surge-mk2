# 生まれた理由とこだわり

!!! summary "要点"
    - 自動運転の手法は数多くあるのに、**「どれが、どんな場面に向いているか」を同じ条件で比べる機会がない**。だから、全部を 1 台で走らせて比べられる車を作りました。
    - どの方式でも、センサの入力・車への指令・安全機構は共通です。**方式を入れ替えても、車と GUI はそのまま**使えます。
    - Raspberry Pi やカメラなどの既製品を除き、**モータドライバからファームウェア、上位のソフト、GUI まで自作**しています。

## きっかけ

大学でロボティクスを学ぶ中で、自動運転の手法は数多くあるのに、「どれが、どんな場面に向いているのか」を同じ条件で比べる機会がありませんでした。
論文や教科書の手法を、実際に走る 1 台の車で全部試して比べたい。
車やモータースポーツが好きだったこともあり、そのための車を自分で作ることにしました。

**「自動運転の手法を、1 台の車で全部走らせて比べる」ためのロボティクスの実験場**――それが SURGE Mark.2 です。


## こだわり

### 手法を公平に比べられる土台

どの方式でも、センサの入力、車への指令、安全機構は共通です。
方式を追加しても、車や GUI の作りを変えずに済みます（[走行モード](../autonomy/modes/index.md#planner-の約束)）。

### 安全を最優先に分担する

判断は Raspberry Pi、リアルタイム制御は STM32 と分けました。
Raspberry Pi が固まる、通信が切れるといった異常でも、ハートビートが止まったことを STM32 が検知して車を止めます。
電源を入れただけで走り出す経路もありません（[安全層](../control/safety.md)）。

### シミュレータと実機をつなぐ

実機の特性を再現したシミュレータで先に検証し、同じ走行ログで複数の手法を比べます（[検証の仕組み](../development/workflow.md)）。

### 測って、車を知る

路面や車の状態は、計算だけでは分かりません。
走行ログから車の物理パラメータを求める校正のツールを作り、測って確かめながら制御を作り込みました。
路面のグリップのように日によって変わる条件は、走行中に学習して速度や走行ラインに反映します。

### ほぼ全部を自作する

Raspberry Pi やカメラなどの既製品以外は、モータドライバを含めて自作です。
基板・ファームウェア・上位のソフト・GUI まで、すべて自分で設計しました。
後輪の**インホイール・ダイレクトドライブ**もその 1 つです（[インホイール・ダイレクトドライブ](../hardware/in-wheel-drive.md)）。

## 一番の苦労は制御の設計

実機には、教科書どおりにいかない点がたくさんありました。

- **ステアリング**は、モータの角度と路面の舵角が比例しません。実機で測った特性から換算式を作りました（[ステアリング](../hardware/steering.md)）。
- **車速センサ**は分解能が粗く、そのまま微分しても加速度には使えません。加速度センサと組み合わせたカルマンフィルタで補いました（[駆動制御](../control/drive.md)）。
- **モータドライバ**は、最初の基板では電流を測れませんでした。作り直しを重ね、4 代目の基板で相電流を測って、トルクを N·m 単位で出せるようになりました（[自作モータドライバ](../hardware/motor-driver.md)）。

## これから

今の E2E（入力から操舵を直接出す、学習型の自動運転）は、LiDAR だけ、またはカメラだけを入力にしています。
次は、**両方を組み合わせた E2E の自動運転**に挑戦します。
LiDAR は距離に強く、カメラは路面や白線などの見た目に強いので、互いの弱点を補えると考えています。
同じ車・同じ環境で単独の方式と比べ、効果を数字で確かめます。

ハードウェアでは、車輪の軸受け、タイヤ（コーキング剤で成形する自作タイヤ）、モータドライバの角度センサの読み方に改善の予定があります（[インホイール・ダイレクトドライブ](../hardware/in-wheel-drive.md#今後の改善点)）。
